# Public Solution Intelligence backend

This is the FastAPI backend for Technathon PS12. Its PostgreSQL foundation
includes the initial core ORM model and Alembic migration only; it has no report
APIs, analytics, AI integrations, or sample data.

## Setup

From the `backend` directory, create and activate a virtual environment:

### Windows PowerShell

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
```

### macOS/Linux

```bash
python3 -m venv .venv
source .venv/bin/activate
```

Install the initial dependencies:

```bash
pip install -r requirements.txt
```

## Windows database configuration

The backend reads `DATABASE_URL` from the Windows process environment. Use the
following format, replacing only the placeholders in your local terminal:

```text
postgresql+psycopg://USERNAME:PASSWORD@localhost:5432/public_solution_intelligence
```

For the current PowerShell session, set it before starting Uvicorn:

```powershell
$env:DATABASE_URL = "postgresql+psycopg://USERNAME:PASSWORD@localhost:5432/public_solution_intelligence"
```

To retain the value for future terminals, use `setx` (then close and reopen
PowerShell):

```powershell
setx DATABASE_URL "postgresql+psycopg://USERNAME:PASSWORD@localhost:5432/public_solution_intelligence"
```

`CORS_ALLOW_ORIGINS` is optional and defaults to common local React development
origins. `.env.example` documents both variable formats, but the application
does not load a `.env` file automatically; set the variables in the terminal or
through Windows environment settings. Never commit real credentials.

## Run

With the virtual environment active, run:

```powershell
uvicorn app.main:app --reload
```

The server starts at `http://127.0.0.1:8000`.

## Health check

Open `http://127.0.0.1:8000/api/v1/health`, or run:

```powershell
curl http://127.0.0.1:8000/api/v1/health
```

Expected response:

```json
{
  "status": "ok",
  "service": "public-solution-intelligence",
  "database": "connected"
}
```

If PostgreSQL is stopped, the URL is absent, or credentials are invalid, the
endpoint responds with HTTP `503 Service Unavailable` and a database-unavailable
detail instead of reporting a healthy service.

## Database schema and migrations

The core schema uses UUID primary keys consistently. UUIDs are generated by the
application, so PostgreSQL extensions are not required and future mobile/API
clients can create identifiers without depending on a single database sequence.
All lifecycle timestamps use PostgreSQL `TIMESTAMP WITH TIME ZONE`.

The existing initial migration is already included at
`alembic/versions/20260912_0001_initial_core_schema.py`. Do **not** create a
second initial revision. Apply it from the `backend` directory after setting
`DATABASE_URL`:

```powershell
alembic upgrade head
alembic current
```

To verify the tables with SQLAlchemy (without requiring the PostgreSQL `psql`
command to be on PATH), run:

```powershell
python -c "from sqlalchemy import create_engine, inspect; import os; print(inspect(create_engine(os.environ['DATABASE_URL'])).get_table_names())"
```

For future deliberate schema changes, create a revision after updating the ORM
models, inspect the generated migration, then apply it:

```powershell
alembic revision --autogenerate -m "describe_schema_change"
alembic upgrade head
```

The initial migration creates these tables: `users`, `reports`, `ai_analysis`,
`hotspots`, `hotspot_reports`, `interventions`, `impact_metrics`, and
`report_status_history`, plus Alembic's version table. Images are represented
only by `reports.image_path`; no image binary data is stored in PostgreSQL.

## Initial Reports API

The API now exposes only these report endpoints:

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/v1/reports` | Create a multipart report, with an optional image. |
| `GET` | `/api/v1/reports/{report_id}` | Retrieve one report by UUID. |
| `GET` | `/api/v1/reports` | List reports with simple pagination and filters. |
| `GET` | `/api/v1/reports/my` | List reports for the temporary development user. |

`POST /api/v1/reports` accepts these multipart fields: `issue_category`,
`description`, `latitude` (-90 to 90), `longitude` (-180 to 180),
`reported_at` (ISO-8601 with a timezone offset), `severity` (`low`, `medium`,
`high`, or `critical`), and optional `image` (`.jpg`, `.jpeg`, `.png`, or
`.webp`). The maximum upload size defaults to 5 MiB and is configurable through
`MAX_IMAGE_SIZE_BYTES`.

For this temporary development phase, report creation and `/reports/my` require
an `X-Development-User-Id` header containing the UUID of an **already
provisioned** user. This is not authentication, does not create a user, and is
isolated in `app/api/dependencies.py` so a future JWT dependency can replace it.

Create a report without an image:

```powershell
curl.exe -X POST http://127.0.0.1:8000/api/v1/reports `
  -H "X-Development-User-Id: EXISTING-USER-UUID" `
  -F "issue_category=Road Damage" `
  -F "description=A pothole blocks part of the lane." `
  -F "latitude=28.6139" `
  -F "longitude=77.2090" `
  -F "reported_at=2026-09-12T10:30:00+05:30" `
  -F "severity=high"
```

Include an optional image using the same request:

```powershell
curl.exe -X POST http://127.0.0.1:8000/api/v1/reports `
  -H "X-Development-User-Id: EXISTING-USER-UUID" `
  -F "issue_category=Road Damage" `
  -F "description=A pothole blocks part of the lane." `
  -F "latitude=28.6139" `
  -F "longitude=77.2090" `
  -F "reported_at=2026-09-12T10:30:00+05:30" `
  -F "severity=high" `
  -F "image=@C:\path\to\issue.jpg;type=image/jpeg"
```

A successful create response is HTTP `201` and follows this shape:

```json
{
  "id": "REPORT-UUID",
  "user_id": "EXISTING-USER-UUID",
  "issue_category": "Road Damage",
  "description": "A pothole blocks part of the lane.",
  "latitude": 28.6139,
  "longitude": 77.209,
  "reported_at": "2026-09-12T10:30:00+05:30",
  "severity": "high",
  "status": "pending",
  "image_path": "uploads/reports/generated-file.jpg",
  "created_at": "2026-09-12T05:00:00Z",
  "updated_at": "2026-09-12T05:00:00Z"
}
```

List reports with `page` (default `1`) and `page_size` (default `20`, maximum
`100`). Optional filters are `category`, `status` (`pending`, `in_progress`,
`resolved`), and `severity`.

```powershell
curl.exe "http://127.0.0.1:8000/api/v1/reports?page=1&page_size=20&status=pending"
curl.exe -H "X-Development-User-Id: EXISTING-USER-UUID" http://127.0.0.1:8000/api/v1/reports/my
curl.exe http://127.0.0.1:8000/api/v1/reports/REPORT-UUID
```

Uploaded images are saved to a backend-managed `uploads/reports` directory
under a generated UUID filename. The original filename is never used, so it
cannot traverse paths; only the logical `uploads/reports/...` reference is
stored in PostgreSQL. If the report transaction fails, the just-saved file is
removed.

## Local LLM text analysis

The backend includes a small, replaceable text-analysis service that calls a
local llama.cpp server exposing an OpenAI-compatible chat-completions API.
This milestone keeps the FastAPI endpoint stable even if the underlying model or
runtime changes in the future. The default local model is
`Qwen2.5-3B-Instruct-GGUF:Q4_K_M`, running through llama.cpp and a local HTTP
server.

Set these values in your active PowerShell session before starting the backend:

```powershell
$env:LLM_ENABLED = "true"
$env:LLM_BASE_URL = "http://127.0.0.1:8081/v1"
$env:LLM_MODEL_NAME = "Qwen2.5-3B-Instruct-GGUF:Q4_K_M"
$env:LLM_TEMPERATURE = "0.1"
$env:LLM_MAX_TOKENS = "256"
$env:LLM_TIMEOUT_SECONDS = "30"
```

### Local llama.cpp server startup

Start the local model server with the downloaded Qwen model already present on the development machine:

```powershell
llama-server -m "Qwen2.5-3B-Instruct-GGUF:Q4_K_M" --host 127.0.0.1 --port 8081 --ctx-size 4096
```

The exact model name may vary slightly by local installation, but the project is
configured to use the already-downloaded `Qwen2.5-3B-Instruct-GGUF:Q4_K_M`
quantized model through llama.cpp. The FastAPI layer never trains or fine-tunes
model weights and does not persist model output in PostgreSQL.

### AI analysis endpoint

Authority users may call this endpoint:

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/v1/ai/text-analyze` | Analyze a citizen-selected category and description via the local model |

The request body is:

```json
{
  "issue_category": "Road Damage",
  "description": "Large pothole near the main bus stop and vehicles are having difficulty passing."
}
```

The response contract is:

```json
{
  "analysis_available": true,
  "issue_category": "Road Damage",
  "summary": "Large pothole near the bus stop.",
  "keywords": ["pothole", "bus stop"],
  "category_consistent": true,
  "urgency_indicators": ["large pothole"],
  "hazard_indicators": ["vehicles struggling to pass"],
  "confidence": 0.82,
  "needs_review": false,
  "explanation": "Text supports a road hazard."
}
```

The model response is always validated by Python before it is returned. The
service enforces:

- valid JSON is required;
- required fields must exist and be the correct type;
- `confidence` must be a real numeric value between `0.0` and `1.0` inclusive;
- `issue_category` must match the citizen-selected category after trimming and
  case-insensitive comparison;
- `keywords`, `urgency_indicators`, and `hazard_indicators` must be lists of
  strings;
- `needs_review` and `category_consistent` must be booleans;
- unexpected model fields are ignored and never leak into the public API
  response;
- invalid model output or a failed server call returns a controlled fallback
  result with `analysis_available=false`, `needs_review=true`, and a clear
  explanation.

The fallback response is intentionally conservative:

```json
{
  "analysis_available": false,
  "issue_category": "Road Damage",
  "summary": "",
  "keywords": [],
  "category_consistent": false,
  "urgency_indicators": [],
  "hazard_indicators": [],
  "confidence": 0.0,
  "needs_review": true,
  "explanation": "LLM analysis unavailable or failed validation."
}
```

The endpoint uses the same temporary authority-only mechanism as the analytic
endpoints: the caller must supply `X-Development-User-Id` and that user must
have the `authority` role. Citizens receive HTTP `403`.

The prompt is centralized and includes responsible-AI instructions summarizing
that the model must not identify people, profile citizens, judge reliability,
create operational recommendations, or determine whether any report is true.
The model is used only to interpret observable text and return the requested
structured fields; it is not used to calculate final risk, create intervention
records, or make autonomous decisions.

Trend detection, severity aggregation, risk scoring, and recommendations remain
unchanged. The AI endpoint is read-only and intentionally isolated from the
existing report submission flow.

## Local VLM image validation

The backend also exposes a separate, replaceable visual validation service for
the already downloaded `Qwen2.5-VL-3B-Instruct-GGUF:Q4_K_M` model. It runs
through a second local llama.cpp server because the text LLM uses port `8081`
and Apache occupies port `8080`.

Configure the VLM independently:

```powershell
$env:VLM_ENABLED = "true"
$env:VLM_BASE_URL = "http://127.0.0.1:8082/v1"
$env:VLM_MODEL_NAME = "Qwen2.5-VL-3B-Instruct-GGUF:Q4_K_M"
$env:VLM_TEMPERATURE = "0.1"
$env:VLM_MAX_TOKENS = "128"
$env:VLM_TIMEOUT_SECONDS = "30"
```

The default VLM endpoint is configurable through `VLM_BASE_URL`; `8082` is
only the development default and must not be treated as a fixed architectural
port.

Start the separate VLM server with llama.cpp:

```powershell
llama-server -hf Qwen2.5-VL-3B-Instruct-GGUF:Q4_K_M `
  --host 127.0.0.1 `
  --port 8082 `
  --ctx-size 4096
```

### VLM endpoint

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/v1/ai/image-validate` | Check visible image consistency with the selected category |

The endpoint accepts multipart form data:

- `issue_category`: the citizen-selected category
- `image`: a JPG, PNG, or WEBP upload

The image is read in memory for the request and is sent to llama.cpp as a
base64 `data:` URI in the OpenAI-compatible multimodal `image_url` message
content. It is not stored in PostgreSQL or persisted by the VLM service.

Example request:

```powershell
curl.exe -X POST http://127.0.0.1:8000/api/v1/ai/image-validate `
  -H "X-Development-User-Id: EXISTING-USER-UUID" `
  -F "issue_category=Road Damage" `
  -F "image=@C:\path\to\road-damage.jpg;type=image/jpeg"
```

The response is constrained to:

```json
{
  "analysis_available": true,
  "issue_category": "Road Damage",
  "image_consistent": true,
  "validation_result": "YES",
  "confidence": 0.9,
  "needs_review": false,
  "explanation": "The visible image evidence is consistent with the selected category."
}
```

`validation_result` is exactly one of `YES`, `NO`, or `UNCERTAIN`:

- `YES`: visible evidence is consistent with the selected category.
- `NO`: visible evidence appears inconsistent with the selected category.
- `UNCERTAIN`: the image is blurry, dark, obstructed, ambiguous, or otherwise
  insufficient. `UNCERTAIN` always sets `needs_review=true`; it is never
  converted to `NO`.

Python validation is authoritative. It rejects malformed JSON, missing fields,
unexpected types, unknown result values, category changes, and confidence
values outside `0.0..1.0`. A value such as `confidence=100` is rejected rather
than normalized. Unexpected model fields are not returned publicly.

If the VLM is disabled, unavailable, times out, returns malformed output, or
fails validation, the endpoint returns a controlled fallback with
`analysis_available=false`, `validation_result="UNCERTAIN"`,
`confidence=0.0`, and `needs_review=true`. The report is not rejected
automatically.

The VLM uses the existing `X-Development-User-Id` mechanism. Any existing
citizen or authority development user may call this read-only preprocessing
endpoint; nonexistent users are rejected. Citizens do not receive access to
administrative analytics or operational endpoints.

The centralized VLM prompt instructs the model not to identify people,
recognize faces, infer identity or personal traits, judge citizens, determine
responsibility, accuse anyone, verify report truth, predict events, or make
operational recommendations. The VLM only checks visible category consistency;
human authorities remain responsible for final decisions.

Manual verification should use three real images with the same request:

1. Road Damage category plus a road-damage image should return `YES`.
2. Road Damage category plus a garbage image should return `NO`.
3. Road Damage category plus a blurry or unclear image should return
   `UNCERTAIN` and `needs_review=true`.

The VLM endpoint is read-only, does not persist arbitrary output, does not add
database tables, and does not modify the existing text LLM endpoint.

Run the API tests without a PostgreSQL password:

```powershell
pip install -r requirements-dev.txt
python -m pytest -q
```

The tests use an in-memory SQLite database and create their own isolated test
user; they do not create PostgreSQL data or require a running PostgreSQL server.

## Severity aggregation

Authority users can inspect the recorded severity distribution for persisted
hotspots:

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/v1/analytics/severity/{hotspot_id}` | Aggregate one hotspot |
| `GET` | `/api/v1/analytics/severity` | Aggregate all persisted hotspots |

Both endpoints require the temporary `X-Development-User-Id` header for an
existing authority user; citizen users receive HTTP `403`. Optional `category`,
`from`, and `to` query parameters filter reports. Category matching trims
whitespace and is case-insensitive. `from` and `to` are inclusive and must be
timezone-aware; report timestamps and filters are normalized to UTC.

The supported stored severity vocabulary is `low`, `medium`, `high`, and
`critical`, mapped centrally to numeric values `1`, `2`, `3`, and `4`.
`weighted_severity_average` is the sum of valid numeric values divided by the
number of valid severity reports. `severity_index_percent` normalizes that
average with `((average - 1) / 3) * 100`; it is an aggregation evidence value,
not the final PS12 risk score. Severity percentages use the valid-severity
count as their denominator.

Null, unknown, or otherwise invalid stored severity values increment
`invalid_severity_reports` and are excluded from severity counts, percentages,
the weighted average, and the index. When no valid severity values exist, the
weighted average and index are both `0`; no severity evidence is fabricated.
The service is read-only and does not require a schema migration.

Severity aggregation summarizes the severity values recorded in reports. It
does not prove that a real-world hazard exists and is not the final PS12 risk
score.

## Explainable hotspot risk score

Authorities can calculate a read-only, on-demand prioritization signal for a
persisted hotspot:

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/v1/analytics/risk/{hotspot_id}` | Score one hotspot |
| `GET` | `/api/v1/analytics/risk` | Score all persisted hotspots |

Both endpoints require `X-Development-User-Id` for an authority user; citizens
receive HTTP `403`. Optional `category`, `from`, and `to` filters are supported.
Categories are trimmed and compared case-insensitively. Date filters must
include offsets, are normalized to UTC, and use inclusive boundaries.

The score is the bounded sum of six deterministic weighted components. The
default weights total exactly 100:

| Component | Weight | Normalization |
|---|---:|---|
| Spatial concentration | 20 | linked report count / `RISK_SPATIAL_REPORT_COUNT_CAP` |
| Temporal activity | 20 | current reports per day / `RISK_TEMPORAL_FREQUENCY_CAP` |
| Recurrence | 15 | `none=0`, `low=33.33`, `moderate=66.67`, `high=100` |
| Trend | 15 | `increasing=100`, `stable=50`, `decreasing=0`, insufficient=0 |
| Severity | 20 | existing `severity_index_percent` |
| Related reports | 10 | related linked reports / `RISK_DUPLICATE_COUNT_CAP` |

For every component:

```text
component_percent = min(observed_value / cap, 1) * 100
component_points = component_percent * component_weight / 100
```

The final score is the sum of component points, rounded to two decimal places,
and clamped to `0..100`. Risk levels are deterministic:

```text
0-24.99   low
25-49.99  moderate
50-74.99  high
75-100    critical
```

Defaults are configurable through environment variables:

```text
RISK_SPATIAL_WEIGHT=20
RISK_TEMPORAL_WEIGHT=20
RISK_RECURRENCE_WEIGHT=15
RISK_TREND_WEIGHT=15
RISK_SEVERITY_WEIGHT=20
RISK_DUPLICATE_WEIGHT=10
RISK_SPATIAL_REPORT_COUNT_CAP=10
RISK_TEMPORAL_FREQUENCY_CAP=2
RISK_DUPLICATE_COUNT_CAP=5
```

Configuration is validated before scoring: weights must be finite,
non-negative, and sum to exactly 100; normalization caps must be positive and
finite. Invalid configuration fails clearly rather than producing a score.

The score composes existing temporal, recurrence, trend, severity, and
duplicate-analysis services without changing their behavior. Missing evidence
is exposed in each response component with `available=false` and a reason.
Missing evidence contributes a deterministic zero or neutral value: empty
spatial/temporal/recurrence evidence contributes zero, insufficient trend
contributes zero, and the existing zero-valid-severity behavior contributes
zero. Related-report evidence counts unique related reports within the
selected hotspot and filters. It is corroborating reporting activity, not a
finding that any citizen is dishonest.

Example calculation: spatial `80% * 20% = 16` points, temporal `60% * 20% =
12`, recurrence `66.67% * 15% = 10`, trend `100% * 15% = 15`, severity `75% *
20% = 15`, and related reports `50% * 10% = 5`; the final score is `73`.
The response includes each percentage, weight, points, availability, evidence
summary, and final level so the result is reproducible.

The risk score prioritizes public-space locations using observable report
patterns. It does not profile individuals, predict individual behavior,
determine report truth, or prove that a real-world hazard exists. The score is
an explainable aggregation of deterministic evidence components, not an
autonomous decision. Humans remain responsible for final operational
decisions.

## Deterministic hotspot recommendations

Authorities can request read-only candidate actions for a persisted hotspot:

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/v1/recommendations/{hotspot_id}` | Recommend actions for one hotspot |
| `GET` | `/api/v1/recommendations` | Recommend actions for all persisted hotspots |

Both endpoints require `X-Development-User-Id` for an authority user; citizens
receive HTTP `403`. Optional `category`, `from`, and `to` filters use the same
trimmed, case-insensitive category matching and timezone-aware UTC-normalized
inclusive date boundaries as the existing analytics services. Invalid date
ranges return HTTP `422`.

Recommendations are generated by a centralized deterministic rule engine. It
reuses the existing risk score, severity, temporal, recurrence, trend, and
related-report evidence. The existing risk score directly determines priority:

```text
75-100    critical
50-74.99  high
25-49.99  moderate
0-24.99   low
```

Known category rules are:

| Category | Candidate action | Type |
|---|---|---|
| Road Damage | Inspect and repair damaged road surface | `repair` |
| Garbage Overflow | Schedule garbage collection and inspect overflow point | `schedule_collection` |
| Water Leakage | Inspect water line/leak source and arrange repair | `repair` |
| Street Light Issue | Inspect street-light equipment and arrange repair/replacement | `replace` |

Unknown categories receive the controlled generic action
`Perform a general public-space inspection` with type `inspect`; no
category-specific action is invented. When no reports match a persisted
hotspot, the service returns only a low-priority routine monitoring
recommendation.

Evidence rules may add a small number of supporting candidate actions:

- high severity evidence supports prioritized field inspection;
- an increasing trend supports prompt investigation and monitoring;
- high recurrence supports recurring inspection or permanent corrective action;
- related-report evidence supports checking whether reports describe the same
  underlying issue.

Every returned recommendation includes its action type, priority, category,
reason, and directly observable evidence. Missing evidence is omitted from the
reason rather than fabricated. Recommendations are not persisted and do not
create intervention records; an authority must explicitly use the existing
intervention API if an action is approved.

For example, several Road Damage reports with critical severity, increasing
activity, and high recurrence produce the existing risk score first. That score
sets recommendation priority, while the category rule produces
`Inspect and repair damaged road surface`; the reason identifies the linked
category and increasing activity. Related reports may add a separate
corroboration/checking recommendation, without treating any citizen as
unreliable.

Recommendations are deterministic candidate actions derived from observable
public-space reporting evidence. They do not prove that a hazard exists and do
not make autonomous operational decisions. The system does not profile
individuals, identify responsible persons, or judge citizen reliability. The
authority remains responsible for deciding whether and how to act.

## Intervention impact measurement API

Authorities can record transparent, prototype impact measurements using the
existing `hotspots`, `interventions`, `reports`, and `impact_metrics` tables.
Every endpoint below requires the temporary `X-Development-User-Id` header for
an existing user whose role is `authority`; citizen users receive HTTP 403.

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/v1/impact/{hotspot_id}/snapshot` | Calculate the current hotspot snapshot |
| `POST` | `/api/v1/impact/{hotspot_id}/measure` | Store before/after intervention impact |
| `GET` | `/api/v1/impact/{hotspot_id}` | Return the latest hotspot impact |
| `GET` | `/api/v1/impact/interventions/{intervention_id}/impact` | Return impact for an intervention |

Snapshots and measurements use a configurable service constant of **7 days**.
For a measurement timestamp, the report window is the inclusive interval from
`timestamp - 7 days` through `timestamp`. Report frequency is the number of
reports linked to the hotspot through `hotspot_reports`, divided by 7. No
unlinked or unrelated reports are counted.

The risk score is the stored `hotspots.risk_score`; this milestone does not
implement a risk engine or historical risk reconstruction. Because the current
schema does not provide enough historical recurrence data, recurrence is
returned as `not_available` rather than inventing a value. Consequently, risk
reduction is zero when the same current stored risk score is used for both
sides.

Reduction percentages use:

```text
(before - after) / before * 100
```

The result is clamped to 0–100. If the baseline is zero or negative, the
percentage is safely returned as 0 to avoid division by zero.

Example snapshot request:

```powershell
curl.exe -X POST http://127.0.0.1:8000/api/v1/impact/HOTSPOT-UUID/snapshot `
  -H "X-Development-User-Id: AUTHORITY-USER-UUID" `
  -H "Content-Type: application/json" `
  -d '{\"measured_at\":\"2026-09-14T12:00:00+05:30\"}'
```

Example measurement request:

```json
{
  "intervention_id": "INTERVENTION-UUID",
  "before_measured_at": "2026-09-01T12:00:00+05:30",
  "after_measured_at": "2026-09-14T12:00:00+05:30"
}
```

Measurements require an existing intervention belonging to the requested
hotspot. Completed interventions can use their stored `started_at` and
`completed_at`; active interventions require an explicit after timestamp.
Missing relationships, invalid time ordering, and timezone-less timestamps are
rejected. The prototype measures observed report-window changes only; it does
not forecast outcomes or claim causal attribution.

## Duplicate and related-report analysis

Duplicate analysis is a deterministic, read-only analysis. It never deletes,
merges, or marks a citizen report as false. A report is considered likely
related only when all three observable rules match:

1. `issue_category` matches after trimming whitespace and ignoring case.
2. The geographic distance is at most **50 meters** by default.
3. The absolute reporting-time difference is at most **24 hours** by default.

The thresholds are configurable with the
`DUPLICATE_SPATIAL_THRESHOLD_METERS` and
`DUPLICATE_TEMPORAL_THRESHOLD_HOURS` environment variables. Distance uses the
Haversine formula over latitude/longitude coordinates. Both boundaries are
inclusive.

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/v1/analytics/duplicates/check/{report_id}` | Analyze one report |
| `GET` | `/api/v1/analytics/duplicates` | List detected relationships for authority analysis |

These endpoints require an existing authority development user through
`X-Development-User-Id`. The list endpoint supports optional `category`, `from`,
and `to` filters. Relationships are computed on demand from the existing
`reports` table; no schema addition or relationship table is required for this
milestone.

Example:

```powershell
curl.exe -X POST http://127.0.0.1:8000/api/v1/analytics/duplicates/check/REPORT-UUID `
  -H "X-Development-User-Id: AUTHORITY-USER-UUID"
```

```json
{
  "report_id": "REPORT-UUID",
  "related_reports": [
    {
      "report_id": "RELATED-REPORT-UUID",
      "distance_meters": 12.4,
      "time_difference_hours": 2.1,
      "same_category": true,
      "reasons": [
        "issue categories match",
        "distance is within 50 meters",
        "time difference is within 24 hours"
      ]
    }
  ],
  "likely_duplicate": true
}
```

This is not final recurrence or hotspot intelligence. Exact category labels,
GPS accuracy, report timing, and fixed thresholds can produce false positives
or false negatives. The result means only that reports may describe the same
underlying issue; it does not accuse or penalize the reporting citizen.

## DBSCAN geographic hotspot detection

Authority users can run deterministic spatial clustering over the existing
report coordinates:

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/v1/analytics/hotspots/detect` | Run DBSCAN and persist detected clusters |
| `GET` | `/api/v1/analytics/hotspots` | List persisted detected hotspots |

Both endpoints require an existing authority user through
`X-Development-User-Id`. The default DBSCAN parameters are:

```text
HOTSPOT_DBSCAN_RADIUS_METERS=75
HOTSPOT_DBSCAN_MIN_SAMPLES=3
```

They can be changed through environment variables. Latitude and longitude are
converted to radians, and scikit-learn DBSCAN uses the Haversine metric with
`epsilon = radius_meters / 6,371,000`. This accounts for geographic distance
without requiring PostGIS.

Only finite coordinates within latitude `[-90, 90]` and longitude `[-180, 180]`
are analyzed. Malformed coordinates are skipped. DBSCAN noise points are
reported in the summary but never become hotspots. Each cluster center is the
transparent arithmetic mean of its member latitudes and longitudes.

For every clustered report, a row is ensured in `hotspot_reports`. Re-running
detection with the same cluster membership reuses the existing hotspot and
does not create duplicate hotspot rows or relationships. Existing unrelated
hotspots are preserved. Detection updates the center and report count of a
matching detected cluster but does not calculate risk, trend, recurrence, or
severity. All writes are committed as one transaction and rolled back on
database failure.

Example:

```powershell
curl.exe -X POST http://127.0.0.1:8000/api/v1/analytics/hotspots/detect `
  -H "X-Development-User-Id: AUTHORITY-USER-UUID"
```

```json
{
  "clusters_detected": 1,
  "reports_analyzed": 10,
  "reports_clustered": 8,
  "noise_reports": 2,
  "hotspots": [
    {
      "hotspot_id": "HOTSPOT-UUID",
      "latitude": 28.61395,
      "longitude": 77.20902,
      "report_count": 8
    }
  ]
}
```

Hotspot detection identifies geographic concentrations of reports. It does not
determine whether any individual report is true or false. It is not final
hotspot intelligence and does not prove a real-world hazard. Later PS12 work
may combine spatial clustering with temporal patterns, recurrence, severity,
related reports, and explainable risk scoring.

## Temporal report analysis

Authority users can inspect observable reporting-time patterns without changing
any report data:

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/v1/analytics/temporal` | Analyze report timing |

The endpoint supports optional `hotspot_id`, `category`, `from`, `to`, and
`window_days` filters. A hotspot filter uses only reports linked through
`hotspot_reports`; without it, the service uses the `reports` table directly.
The default comparison window is configurable with
`TEMPORAL_ANALYSIS_WINDOW_DAYS` and defaults to **7 days**. The previous period
is the immediately preceding window of the same length.

The response includes total reports, counts by UTC hour, UTC weekday, calendar
date, peak hour, peak weekday, and four time-of-day groups:

```text
morning:   06:00–11:59
afternoon: 12:00–16:59
evening:   17:00–21:59
night:     22:00–05:59
```

These boundaries are configurable through
`TEMPORAL_MORNING_START_HOUR`, `TEMPORAL_AFTERNOON_START_HOUR`,
`TEMPORAL_EVENING_START_HOUR`, and `TEMPORAL_NIGHT_START_HOUR`.

Frequency is calculated as:

```text
current_report_frequency = current_reports / window_days
previous_report_frequency = previous_reports / window_days
frequency_change_percent =
    (current_frequency - previous_frequency) / previous_frequency * 100
```

When the previous frequency is zero, `frequency_change_percent` is returned as
`0` rather than dividing by zero. Reports on the current window boundaries are
included; the previous window includes its start and excludes the current
window start so the periods do not overlap.

Report timestamps must include timezone offsets. They are normalized to UTC
before hour, weekday, date, and window comparisons, preserving the represented
instant across offsets. A timezone-less `from` or `to` value is rejected with
HTTP 422. A nonexistent hotspot returns HTTP 404, an invalid range returns
HTTP 422, and citizen users receive HTTP 403.

Example:

```powershell
curl.exe "http://127.0.0.1:8000/api/v1/analytics/temporal?category=Road%20Damage&window_days=7" `
  -H "X-Development-User-Id: AUTHORITY-USER-UUID"
```

Temporal analysis identifies observable reporting patterns over time. It does
not prove that a location is unsafe or that a report is true or false. It does
not implement recurrence intelligence, trend prediction, risk scoring,
recommendations, or causal attribution.

## Recurrence detection

Authority users can inspect whether reports linked to a persisted hotspot recur
across separate time periods:

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/v1/analytics/recurrence/{hotspot_id}` | Analyze one hotspot |
| `GET` | `/api/v1/analytics/recurrence` | Analyze all persisted hotspots |

Both endpoints use the existing `X-Development-User-Id` header and require an
authority user. Optional filters are `category`, `from`, `to`, `period_days`,
and `analysis_window_days`. Category matching trims whitespace and ignores
case. Recurrence never creates hotspots; DBSCAN remains responsible for
spatial clustering.

Defaults are configurable through:

```text
RECURRENCE_PERIOD_DAYS=7
RECURRENCE_ANALYSIS_WINDOW_DAYS=28
```

The default window contains four seven-day periods. Reports are loaded through
`hotspot_reports`, normalized to UTC, and assigned to deterministic consecutive
period buckets beginning at the analysis-window start. The current window
includes both boundaries; periods before the final one end immediately before
the next period. Exact boundary timestamps therefore belong deterministically
to the following bucket, except the overall window end, which belongs to the
final bucket.

The service returns total reports, observed periods, active periods, each
period's report count, the longest consecutive active-period streak, whether
the current period is active, and:

```text
recurrence_ratio = active_periods / observed_periods
```

Recurrence levels are intentionally simple:

```text
none:     0 active periods
low:      1 active period
moderate: 2 active periods
high:     3 or more active periods
```

Timezone-aware query timestamps are required and converted to UTC before window
comparison and period assignment. Invalid ranges, invalid period lengths, and
missing hotspots return clear HTTP 422 or 404 errors. A hotspot with no matching
reports returns `none` with zero active periods.

Recurrence detection identifies repeated reporting activity across separate time
periods. It does not prove that a real-world hazard exists or that any
individual report is true or false. It is evidence only, not trend prediction,
final risk scoring, a recommendation, or causal attribution.

## Trend detection

Authority users can inspect whether report activity at persisted hotspots is
increasing, decreasing, or stable:

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/v1/analytics/trend/{hotspot_id}` | Analyze one hotspot |
| `GET` | `/api/v1/analytics/trend` | Analyze all persisted hotspots |

Both endpoints require `X-Development-User-Id` for an authority user. Optional
filters are `category`, `from`, `to`, `period_days`, and
`analysis_window_days`. Category matching trims whitespace and ignores case.
The analysis is read-only and uses reports linked through `hotspot_reports`.

Defaults:

```text
TREND_PERIOD_DAYS=7
TREND_ANALYSIS_WINDOW_DAYS=28
```

The requested analysis window is divided into deterministic consecutive buckets
starting at `from`. Reports are normalized to UTC before assignment. The current
window includes both boundaries; an exact period boundary belongs to the
following bucket, except the overall end belongs to the final bucket.

The first and second halves of the observed period counts are averaged:

```text
first_half_average = average(first-half period counts)
second_half_average = average(second-half period counts)
trend_change_percent =
    (second_half_average - first_half_average)
    / first_half_average * 100
```

Classification is intentionally deterministic:

```text
increasing:      second-half average > first-half average
decreasing:      second-half average < first-half average
stable:          averages are equal
insufficient_data: fewer than two periods or first-half average is zero
```

When the first-half average is zero, `trend_change_percent` is returned as `0`
to avoid division by zero and the classification is `insufficient_data`, even
if later periods contain reports. Empty periods inside the requested window are
represented with zero counts; no historical values are fabricated.

Query timestamps must include timezone offsets and are normalized to UTC.
Invalid ranges and period settings return HTTP 422, missing hotspots return
HTTP 404, and citizens receive HTTP 403.

Example:

```powershell
curl.exe "http://127.0.0.1:8000/api/v1/analytics/trend/HOTSPOT-UUID?period_days=7&analysis_window_days=28" `
  -H "X-Development-User-Id: AUTHORITY-USER-UUID"
```

```json
{
  "hotspot_id": "HOTSPOT-UUID",
  "total_reports": 8,
  "observed_periods": 4,
  "period_days": 7,
  "analysis_window_days": 28,
  "period_counts": [
    {"start": "2026-09-01T00:00:00Z", "end": "2026-09-08T00:00:00Z", "report_count": 1},
    {"start": "2026-09-08T00:00:00Z", "end": "2026-09-15T00:00:00Z", "report_count": 1},
    {"start": "2026-09-15T00:00:00Z", "end": "2026-09-22T00:00:00Z", "report_count": 2},
    {"start": "2026-09-22T00:00:00Z", "end": "2026-09-29T00:00:00Z", "report_count": 4}
  ],
  "first_half_average": 1,
  "second_half_average": 3,
  "trend_change_percent": 200,
  "trend": "increasing"
}
```

Trend detection identifies changes in reporting activity over time. It does
not prove that a real-world hazard exists and does not determine whether any
individual report is true or false. It does not implement final risk scoring,
recommendations, forecasting, recurrence changes, or causal attribution.

## Unified report intelligence orchestration

The backend exposes one deterministic orchestration endpoint for an existing
report:

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/v1/ai/analyze-report/{report_id}` | Combine validated text interpretation and optional visual consistency evidence |

The endpoint accepts the existing `X-Development-User-Id` header. Both an
existing citizen development user and an existing authority development user
may request this read-only preprocessing result. It does not grant citizens
access to analytics, risk, recommendations, interventions, or other
administrative endpoints.

For each report, the orchestrator loads only the issue category and
description for the LLM. If the stored image reference resolves safely below
`UPLOADS_DIR`, it passes the image bytes and the original selected category to
the existing VLM service. Python combines only the already validated results;
neither model is asked to combine evidence or calculate risk.

The response contains separate `text_analysis` and `image_analysis` objects,
`evidence_consistency`, `overall_needs_review`, and a deterministic
explanation. The original issue category is always preserved.

Review is required when text is unavailable, text category consistency fails,
either model requests review, VLM output is unavailable, or VLM returns `NO`
or `UNCERTAIN`. When no usable image is supplied, the VLM is not called and
visual analysis is explicitly unavailable; this absence alone does not force
review. If one model fails, the other validated evidence is still returned. If
both fail, analysis is unavailable and review is required.

`NO` means only that the image appears visually inconsistent with the selected
category. It does not mean that a citizen is lying, and it does not determine
whether a report is true or false.

### Persistence and safeguards

The existing one-to-one `ai_analysis` table is reused without a migration.
Validated structured results are stored in its existing text fields together
with the selected category, report timestamp, severity indicator, and VLM
status. Repeated analysis updates the same row rather than creating duplicate
records. Raw unvalidated model output, citizen identity, email, phone, and
image bytes are never stored by this endpoint, and filesystem paths are never
returned.

The LLM interprets citizen-provided text and the VLM checks visible category
consistency. Neither identifies people, profiles citizens, determines
responsibility, verifies report truth, determines final risk, creates
interventions, or makes operational decisions. Human authorities remain
responsible for final decisions.

Manual verification with the local models:

```powershell
$headers = @{ "X-Development-User-Id" = "EXISTING-USER-UUID" }
Invoke-RestMethod `
  -Method Post `
  -Uri "http://127.0.0.1:8000/api/v1/ai/analyze-report/REPORT-UUID" `
  -Headers $headers
```

Run once for an existing report with a road-damage image and once for an
existing report without an image. The text server must be running at the
configured `LLM_BASE_URL`; the VLM server is called only for the image-bearing
report at the configured `VLM_BASE_URL`.
